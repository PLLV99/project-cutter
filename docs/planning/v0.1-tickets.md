# v0.1 — Deposit-only banking core

**Goal:** a running Spring Boot API, backed by PostgreSQL in Docker, that can
create an account, accept a deposit as a double-entry ledger write, and report a
balance derived from that ledger — with tests, pushed to GitHub, and a README
that claims only what is true.

**Time-box: 4 weeks at ~14 h/week.** If week 4 arrives and it is not done, *cut a
ticket*, do not extend the deadline.

**Out of scope — do not build:** auth, withdrawal, transfer, trading, Kafka,
Outbox, AI worker, Redis, frontend, AWS.

**Doc freeze:** no new ADRs, no new lessons, no new learning-records until T10 is
green. The habit is good; it resumes after v0.1 ships.

---

## Ticket format

Each ticket has **TRY / ASK / PROVE / DONE**. `DONE` is the acceptance criteria —
a ticket is not finished until every box is checked.

Nothing below contains implementation code, by design. Ask Claude Code *why*
questions, not *write it for me* questions.

## Week 1 — the database

### T1.1 — PostgreSQL running in Docker
**TRY:** add a Postgres service to `compose.yaml` with a named volume.
**ASK:** "What does a named volume actually do? Where does the data live without one?"
**PROVE:** `docker compose down`, then `up` again. Your data is still there.
**DONE:**
- [ ] `docker compose up -d` starts Postgres
- [ ] You can connect to it from your machine
- [ ] Data survives a `down` / `up` cycle
- [ ] You can explain, out loud, what happens to the data without the volume

### T1.2 — Design the tables on paper, then in SQL
The core of v0.1. Do not rush this.

**TRY:** draw `accounts` and `transactions` on paper first. Decide every column,
its type, and why it exists. Then write the `CREATE TABLE` SQL by hand.
**ASK:** "Why is money stored as `NUMERIC` and never `FLOAT`?" ·
"What breaks if `transactions` has no foreign key to `accounts`?" ·
"In double-entry, what makes a pair of rows balanced?"
**PROVE:** explain out loud why a deposit writes **two** rows, and which one is
the liability side.
**DONE:**
- [ ] `accounts` and `transactions` exist in the database
- [ ] Money columns are `NUMERIC`, never floating point
- [ ] `transactions` has a foreign key to `accounts`
- [ ] There is **no** overwritable `balance` column anywhere
- [ ] Every column choice has a reason you can state in one sentence

## Week 3 — the money operation

### T3.1 — `POST /accounts/{id}/deposit`
The ticket the whole project exists for. Take your time.

**TRY:** a deposit that writes a balanced double-entry pair inside **one**
transaction.
**ASK:** "What happens if the app crashes after the first row and before the
second?" · "What does `@Transactional` guarantee, and what does it not?"
**PROVE:** explain out loud, with the two rows in front of you, why the ledger is
still correct after a crash.
**DONE:**
- [ ] A deposit writes a balanced pair of rows
- [ ] Both rows are written in a single database transaction
- [ ] `400` for a zero or negative amount
- [ ] `404` for an account that does not exist
- [ ] No row anywhere is ever updated in place

### T3.2 — `GET /accounts/{id}` with a derived balance
**TRY:** balance computed by summing the ledger.
**ASK:** "What would go wrong at 10 million transactions? What do real banks do
about it?" — understand the answer; do **not** build it in v0.1.
**DONE:**
- [ ] Balance is summed from `transactions`, never stored
- [ ] A brand-new account reports `0`
- [ ] `404` for an unknown account

### T3.3 — `GET /accounts/{id}/transactions`
**DONE:**
- [ ] Returns the account's transactions, newest first
- [ ] Empty account returns an empty list, not an error
- [ ] `404` for an unknown account
